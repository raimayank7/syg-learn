Linux and Mac commands

Pipes and redirection: join commands together

The idea that makes the command line powerful is simple: small commands that each do one thing, joined so that the output of one becomes the input of the next. This page covers the joining.

Three streams

Every command has three channels.

NameNumberNormally connected to
standard input (stdin)0the keyboard
standard output (stdout)1the screen
standard error (stderr)2the screen

Results go to standard output. Error messages go to standard error, so that they can be separated from results. Redirection reconnects these channels to files or to other commands.

Output into a file: >

Nothing appeared on screen for the first command, because its output went into the file.

Danger. > empties the file before writing. If the file exists, its old contents are gone, with no question asked. In Bash and Zsh, set -o noclobber makes the shell refuse to overwrite with >.

Adding to a file: >>

The pipe

The | sign connects the output of the command on its left to the input of the command on its right.

ls produced a list, and wc -l counted its lines. Pipes can be chained as far as you like.

Read a pipeline from left to right, as a production line: each command receives, changes and passes on.

A real pipeline

Which kinds of message does the log contain, and how many of each?

Step by step: cut takes characters 7 to 11 of each line, where the level is written. sort puts equal lines together. uniq -c collapses them and counts. The final sort -rn puts the largest count first. Four small commands, no programming.

Build a pipeline one stage at a time, running it after each addition to see what the next command will receive.

Input from a file: <

< connects a file to a command's input.

It is less often needed, since most commands accept a file name directly.

Errors

Error messages travel on stream 2, so > alone does not catch them.

The result for notes.txt went to the file. The error for the missing file still came to the screen.

WriteTo send
2> errors.txterrors to a file
2>/dev/nullerrors nowhere: discard them
> all.txt 2>&1both results and errors to one file
&> all.txtthe same, in Bash and Zsh

/dev/null is a special file that discards whatever is written to it. find / -name hosts 2>/dev/null hides the many "Permission denied" lines.

The order matters in > file 2>&1. It says "send output to the file, then send errors to wherever output now goes". Written the other way round, errors still reach the screen.

tee: see it and save it

tee copies its input both to a file and onward to the screen, like a T-shaped pipe joint.

tee -a appends. It is also the way to write to a protected file with sudo, since sudo echo text > file fails: the redirection is done by your own shell, not by sudo. echo text | sudo tee file works.

Running commands one after another

FormMeaning
a ; brun a, then b, whatever happens
a && brun b only if a succeeded
a || brun b only if a failed

&& is the safe way to chain steps. cd project && rm -r tmp deletes only if the cd worked. With a semicolon, a failed cd would leave rm running in the wrong folder.

xargs: turn input into arguments

Some commands take names as arguments, not as input. xargs bridges the gap.

For file names that may contain spaces, use find ... -print0 | xargs -0 ....

Useful commands in pipelines

See sort, uniq, wc and cut.

On Windows

The Command Prompt has the same >, >>, <, |, 2> and &&. The commands on either side are different, but the plumbing works the same way.
