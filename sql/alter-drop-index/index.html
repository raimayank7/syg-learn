Changing tables, dropping them, and indexes

Tables change over time. The business wants to record something new, a column was badly named, an old table is no longer needed. ALTER TABLE changes the structure of a table without touching the rest of its data. DROP TABLE removes a table. This lesson covers both, and then indexes, the main tool for making queries fast.

SQLite cannot change the type of a column or add most constraints to an existing table. The usual way round is to create a new table with the right design, copy the data across with INSERT ... SELECT, drop the old table and rename the new one.

DROP TABLE

DROP TABLE deletes a table: its structure, its data, everything.

CREATE TABLE scratch (note TEXT);
Try it

Result

Done.

DROP TABLE scratch;
Try it

Result

Done.

SELECT * FROM scratch;

What the database says

Error: no such table: scratch

There is no confirmation and, outside a transaction, no undo. Dropping a table that does not exist is an error; DROP TABLE IF EXISTS name avoids that in scripts.

DELETE, TRUNCATE or DROP?

StatementRemovesTable still exists?
DELETE FROM t WHERE ...the rows that matchyes
DELETE FROM tall rowsyes, empty
TRUNCATE TABLE tall rows, quicklyyes, empty
DROP TABLE trows and the table itselfno

Interviewers like this question. DELETE is a data statement and can be filtered. TRUNCATE and DROP are structure statements and cannot.

Indexes: why some searches are fast

Think of the index at the back of a textbook. To find every page that mentions "photosynthesis", you do not read the whole book. You look the word up in the index, which is in alphabetical order, and go straight to the pages.

A database index works the same way. Without one, a search such as WHERE city = 'Delhi' makes the database read every row of the table. That is called a full table scan. With an index on city, it can jump to the matching rows. On twelve rows nobody can tell the difference. On twelve million, it is the difference between a blink and a long wait.

Creating an index

CREATE INDEX idx_customers_city ON customers (city);
Try it

Result

Done.

Give the index a name, the table, and the column. Nothing looks different afterwards. Queries are written exactly as before and return exactly the same rows. The database simply uses the index when it helps.

SELECT name, city FROM customers WHERE city = 'Delhi';
Try it

Result

namecity
Ravi KumarDelhi
Imran AliDelhi

2 rows

An index can cover two columns. The order matters: an index on (status, order_date) helps searches on status alone, or on status and date together, but not on date alone, in the same way that a phone book sorted by surname and then first name is no help in finding everyone called Ravi.

CREATE INDEX idx_orders_status_date ON orders (status, order_date);
Try it

Result

Done.

A unique index also enforces that no two rows share a value.

CREATE UNIQUE INDEX idx_products_name ON products (name);
Try it

Result

Done.

What to index

  • Primary keys are indexed automatically. You never need to do it.
  • Foreign key columns, because joins search on them: orders.customer_id, order_items.order_id, order_items.product_id.
  • Columns that appear often in WHERE.
  • Columns used often in ORDER BY.

What indexes cost

Indexes are not free, which is why you do not index everything.

  • Each index takes disk space.
  • Every INSERT, UPDATE and DELETE must update the indexes as well as the table, so writing gets slower as indexes are added.
  • An index on a column with only a few different values, such as a yes or no flag, rarely helps.
  • As earlier lessons noted, an index on a column is usually ignored when the query wraps the column in a function, or when a LIKE pattern starts with %.

The sensible approach is to add indexes for the queries you really run, and to measure.

Asking the database what it will do

Every database can explain how it plans to run a query. In SQLite, put EXPLAIN QUERY PLAN in front.

EXPLAIN QUERY PLAN
SELECT name FROM customers WHERE city = 'Delhi';
Try it

Result

idparentnotuseddetail
3062SEARCH customers USING INDEX idx_customers_city (city=?)

1 row

The answer mentions the index made above, which shows it is being used. MySQL and PostgreSQL use the word EXPLAIN alone. Reading plans is a skill of its own. For now it is enough to know that the tool exists and that the word "scan" on a big table is the thing to look for.

Removing an index

DROP INDEX idx_products_name;
Try it

Result

Done.

Dropping an index loses no data. Only the speed-up goes. MySQL and SQL Server need the table name too: DROP INDEX idx_products_name ON products.
